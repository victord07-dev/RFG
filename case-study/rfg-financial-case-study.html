Project Overview

Purpose and Context

The project is an MVP finance workflow platform for Reliant Future Group LLP, consisting of a customer Android app scope and a web admin/sales panel. This report focuses on the web admin and sales panel work covered in the provided project details.

01

Project Purpose

The software is intended to support the client's existing physical business workflow. It is not intended to replace manual discussion, physical paperwork, legal documentation, banking processes, finance compliance, tax compliance, collection practices, or regulatory responsibilities.

Scope Focus

The web platform supports loan application recording, customer records, loan status management, EMI status management, payment history, payment reminders, payment settings, activity logs, and restricted sales team access.

Admin Control

Admins can view records, approve or reject applications, mark loans active or closed, edit special terms, approve or reject payment requests, and view reports and logs.

Sales Workflow

Sales users can create applications, enter loan values, add customer, guarantor and showroom details, complete checklist steps, and submit cash payment requests.

No File Upload Storage

The MVP avoids storing Aadhaar, PAN, RC, insurance, pollution, seller ID, customer ID proof, or other sensitive document images/files unless separately agreed later.

Problem Statement and Goals

What the System Needed to Solve

The client needed a practical starting-stage system for staff-led finance operations, while keeping workflows understandable for users who may not be comfortable with complex software.

02

Problem Statement

  • Loan application and customer information needed to be captured in one structured system.
  • Admin review, approval, activation, payment verification, and closure needed clear status control.
  • Cash and normal bank QR payments required manual admin verification because no bank API is used in the MVP.
  • Sales team access needed to be restricted from admin-only controls and from other sales users' records.
  • The design needed to stay simple and readable for branch and field users.

Project Goals

  • Build a web admin panel and restricted sales panel.
  • Use Supabase PostgreSQL for records, roles, policies, and protected workflows.
  • Keep payment verification clear for Razorpay, normal bank QR/manual verification, and cash requests.
  • Use Firebase later for Android EMI reminders.
  • Retain current and previous month logs in Supabase and archive older logs privately to Google Drive.
  • Limit account access to one active admin and two active sales members.

Design Direction

The UI direction uses a light business dashboard style with RFG colors: navy, green, white, soft gray, amber for pending states, and red for rejection or failure states. The interface avoids technical labels and uses practical action language such as Create Application, Approve, Reject, Mark Active, Confirm Payment, and Cash Request.

Process and Workflow

How the Loan Workflow Operates

The workflow is built around a controlled handoff from sales entry to admin review, then activation after actual disbursement, followed by EMI and payment verification activity.

03
1
Sales creates application

Sales records customer details, guarantor details, showroom information, product details, loan values, physical checklist status, and review information.

2
Admin reviews application

Admin approves or rejects the application. If approved, the process continues through discussion, paperwork, and checking.

3
Loan becomes active after disbursement

Admin marks the approved loan active when the customer actually receives funds or the loan cycle should start. The EMI schedule is generated at that point.

4
Sales submits collection request

Sales selects a pending EMI and submits a cash request. Manual bank QR payments also wait for admin verification.

5
Admin confirms or rejects payment

Confirmed payments create a payment record and mark the EMI paid. Rejected requests return the EMI to pending.

Client update included in this report: the application flow now treats the parties as customer, guarantor, showroom, and RFG. Guarantor OTP is planned for configuration later and is not mandatory in the current frontend testing flow.

Solutions Implemented

What Was Delivered

The implementation converted the supplied MVP requirements into an operational web workflow with clear screens, protected backend actions, and a cost-conscious archive plan.

08

Application Control

Admin review, approve, reject, active, closed, special term edits, and MPIN reset workflows were represented in the admin panel.

Payment Verification

Cash and manual bank QR payments wait for admin approval. Confirmed payments become paid records; rejected requests return to pending.

Disbursement-Based EMI

The EMI cycle starts when admin marks the approved loan active after actual disbursement, reducing disputes about starting dates.

Guarantor Flow

The sales application flow now includes guarantor name, number, address, pincode, and a planned guarantor OTP UI.

Free Storage Strategy

Older logs are archived to the client-owned private Google Drive folder instead of filling Supabase storage.

Responsive UI

Admin and sales views were refined for desktop, tablet, and mobile usage with simple language and visible workflows.
